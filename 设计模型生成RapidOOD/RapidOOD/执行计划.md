# RapidOOD 迁移 Spring Boot 可行性分析与执行计划

> 基于 `程序理解.md` 与源码静态分析  
> 结论：**可行，但属于「重平台、保能力」的再工程，而非插件直搬**

---

## 1. 结论摘要

| 维度 | 判断 |
|------|------|
| **整体可行性** | ✅ **可行**（推荐分阶段、后端优先） |
| **直接复制粘贴** | ❌ **不可行**（约 60% 代码与 Eclipse/OSGi/Sirius/Swing 强绑定） |
| **核心能力保留** | ✅ ATL 规则、QMOOD 计算、LLM Prompt 流程均可迁移 |
| **预估工作量** | 小团队 3～6 人月（MVP）；含完整 Web 前端与 RM2PT 解耦约 6～12 人月 |
| **推荐路线** | Spring Boot 无头服务 + Web 前端；EMF/Xtext **Standalone** 或逐步替换为 POJO |

---

## 2. 为什么要迁移（动机）

当前 Eclipse 插件形态的限制：

1. **部署**：必须安装 Eclipse + RM2PT + 多个插件，无法 Web/CI 集成  
2. **协作**：`.remodel` / `.cd` 分散在本地工程，难以多人协作与版本管理  
3. **实验复现**：审稿意见要求的「外部评估、第三方复现」需要 HTTP API 与开放接口  
4. **LLM 集成**：Swing 对话框 + 硬编码 API Key，不适合生产环境  
5. **扩展**：序列图生成、指标优化等论文能力在本仓库未完整实现，Spring Boot 更易迭代

---

## 3. 现有程序分层与迁移难度

### 3.1 可按能力迁移（难度：低～中）

| 能力 | 现有实现 | Spring Boot 对应方案 | 难度 |
|------|----------|----------------------|------|
| 需求→类图转换 | `RunATL` + `GenerateClassDiagram.asm` | 独立 `TransformService`，EMF 加载 `.remodel` 后 headless 跑 ATL | 中 |
| 类图文本解析/序列化 | Xtext `ClassDiagram.xtext` | `ClassDiagramStandaloneSetup` 无 UI 解析/生成 `.cd` | 中 |
| QMOOD 指标 | `Services.java` + `Activator.java` | 抽成纯 Java `MetricsService`，输入 `ClassDiagram` EMF/AST | 低 |
| LLM 职责分配 | `DomainModelDesignDialog` Prompt 逻辑 | `LlmService` + REST；Prompt 模板放 `resources/prompts/` | 低 |
| LLM 领域划分 | 同上 | 同上 | 低 |
| LLM 设计优化 | `DesignModelOptimizationDialog` | 拆为 3 步 API：识别 / 检索 / 生成 | 低 |
| 文件读写 | Eclipse `IFile` / `IProject` | 本地目录 / MinIO / DB BLOB | 低 |

### 3.2 需替换而非迁移（难度：高）

| 能力 | 现有实现 | 问题 | 替代方案 |
|------|----------|------|----------|
| 右键菜单 / Handler | `plugin.xml` + `AbstractHandler` | Eclipse 命令框架 | REST Controller |
| 图形化类图 | Sirius + `.odesign` | 依赖 Eclipse 工作台 | PlantUML 服务端渲染 / Kroki / 前端 diagram-js |
| Swing 对话框 | `JFrame` / `JTabbedPane` | 桌面 UI | Vue3 / React SPA |
| 需求模型编辑器 | `net.mydreamy.requirementmodel` 插件 | 外部 Eclipse 插件，Maven 未必现成 | 见 §4.2 |
| 序列图编辑 | Xtext + Sirius | UI 层 | 前端 Monaco + PlantUML/Mermaid；生成逻辑需新写 |
| OSGi 生命周期 | `Activator` / `MANIFEST.MF` | Spring 不使用 OSGi | `@Configuration` / `@Service` |

### 3.3 本仓库缺失、论文有但需新开发

| 能力 | 说明 |
|------|------|
| Service 类自动生成 | `.atl` 源码不完整，`.asm` 仅有部分 Repository 规则 |
| OCL 合约 → 序列图 | 无 Handler/ATL，需在 Spring Boot 中 **新实现** |
| 规则化指标优化 | 无独立模块，可趁迁移一并实现 |

## 4. 关键技术决策

### 4.1 总体架构（推荐）

```
┌──────────────────────────────────────────────────────────────┐
│  前端（Vue3 / React）                                         │
│  - 需求/类图文本编辑器（Monaco）                               │
│  - PlantUML 预览                                              │
│  - 指标仪表盘、LLM 建议确认流                                  │
└────────────────────────────┬─────────────────────────────────┘
                             │ HTTPS / REST (+ WebSocket 可选)
┌────────────────────────────▼─────────────────────────────────┐
│  Spring Boot 3.x                                              │
│  ┌─────────────┐ ┌──────────────┐ ┌─────────────────────┐  │
│  │ api         │ │ transform    │ │ metrics             │  │
│  │ Controller  │→│ ATL/Java     │→│ QMOOD               │  │
│  └─────────────┘ └──────────────┘ └─────────────────────┘  │
│  ┌─────────────┐ ┌──────────────┐ ┌─────────────────────┐  │
│  │ parser      │ │ llm          │ │ storage             │  │
│  │ Xtext/CD    │ │ OpenAI SDK   │ │ File/MinIO/Postgres │  │
│  └─────────────┘ └──────────────┘ └─────────────────────┘  │
└────────────────────────────┬─────────────────────────────────┘
                             │
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
         .remodel/.cd    OpenAI API    对象存储/数据库
```

### 4.2 需求模型（`.remodel`）依赖——最大风险点

现状：强依赖 Eclipse 插件 `net.mydreamy.requirementmodel`。

可选方案（按推荐顺序）：

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **A. 提取 Standalone JAR** | 从 RM2PT 工程导出 EMF 模型 + Xtext runtime，发布为内部 Maven 模块 | 兼容现有 `.remodel`，ATL 无需改 | 需拿到 RM2PT 源码/构建脚本 |
| **B. 输入改为 JSON/YAML** | 定义 `RequirementModelDTO`，前端或脚本转换 | Spring 生态友好，易测 | 需写适配层，旧文件需迁移工具 |
| **C. 仅支持 XMI** | 用户在 Eclipse 导出 XMI，上传 XMI | 实现快 | 用户体验差 |

**建议**：Phase 1 采用 **A**；并行设计 **B** 作为长期 API 契约。

### 4.3 ATL 在 Spring Boot 中的运行方式

| 方式 | 说明 |
|------|------|
| **保留 ATL（推荐 Phase 1）** | 引入 `org.eclipse.m2m.atl` Maven 依赖（Eclipse Orbit），`RunATL` 改为从 `InputStream`/`URI` 读写，去掉 `IProject` |
| **重写为 Java** | 将 `GenerateClassDiagram.atl` 规则逐条翻译为 `RequirementToClassDiagramTransformer` | 长期维护性更好，初期工作量大 |
| **改用 QVT/Epsilon** | 学术工具链 | 学习成本高，不推荐首版 |

### 4.4 Xtext 在 Spring Boot 中的运行方式

- 使用已有 `ClassDiagramStandaloneSetup.createInjectorAndDoEMFRegistration()`
- 在 `@PostConstruct` 中 **单次注册**，避免重复注册 EMF 包
- 解析：`resource.load()` → 得到 `ClassDiagram` EMF 对象
- 序列化：`NodeModelUtils` 或 `Serializer` 输出文本
- **不要**引入 `*.ui`、Sirius 相关 bundle

### 4.5 前端图形化方案

| 方案 | 适用 |
|------|------|
| **PlantUML + Kroki 服务** | 类图/序列图文本 → PNG/SVG，与现有 `.cd` 格式一致 |
| **plantuml-encoder + 前端渲染** | 轻量，无额外服务 |
| **Mermaid** | 若愿意调整 DSL 语法 |

## 5. 迁移范围建议（三期）

### Phase 1 — MVP 后端（4～6 周）

**目标**：无 Eclipse 依赖的 HTTP 服务，覆盖论文实验最小闭环。

| 功能 | API 示例 |
|------|----------|
| 上传需求模型 | `POST /api/v1/projects/{id}/requirements` |
| 生成类图 | `POST /api/v1/projects/{id}/generate/class-diagram` |
| 获取类图 | `GET /api/v1/projects/{id}/design/class-diagram` |
| 计算指标 | `POST /api/v1/projects/{id}/metrics/evaluate` |
| LLM 职责分配 | `POST /api/v1/llm/assign-responsibility` |
| LLM 优化 | `POST /api/v1/llm/optimize/pattern` |

**交付物**：

- `rapidood-server` Spring Boot 工程
- Docker Compose（可选：Kroki + MinIO）
- Postman/OpenAPI 文档
- 6 个案例（CoCoME 等）自动化脚本

### Phase 2 — Web 前端 + 存储（4～6 周）

- 项目/文件管理（PostgreSQL 元数据 + 对象存储）
- Monaco 编辑 `.cd` / `.remodel`
- 指标历史曲线、LLM 建议「采纳/拒绝」记录（回应审稿意见）
- API Key 走环境变量 / Spring Config，移除硬编码

### Phase 3 — 能力补全与论文对齐（6～8 周）

- OCL → 序列图生成（论文 17 条规则，新模块 `sequence-transform`）
- Service 类生成规则补全
- 规则化指标优化（EntityManager → Repository）
- 纯 MDE baseline 对比接口
- 外部评估：公开数据集下载 + 可重复实验脚本

## 9. 风险与应对

| 风险 | 等级 | 应对 |
|------|------|------|
| RM2PT 插件无法脱离 Eclipse 构建 | 🔴 高 | 提前 Spike；准备 JSON 输入方案 B |
| EMF/ATL 与 Spring Boot 类加载冲突 | 🟠 中 | 独立 ClassLoader 测试；固定 EMF 版本 |
| Xtext Standalone 重复注册 EMF | 🟠 中 | 单例 `EmfRegistryInitializer` |
| LLM 输出不稳定 | 🟠 中 | JSON Schema 校验 + 重试 + 人工确认流 |
| 图形化体验低于 Sirius | 🟡 低 | PlantUML 足够支撑论文演示 |
| 序列图等缺失功能工作量大 | 🟠 中 | 放 Phase 3，MVP 仅类图 |

---

## 10. 不可行或暂不推荐的做法

1. **把整个 Eclipse 打包进 Spring Boot Fat Jar** — 体积巨大、启动慢、维护不可持续  
2. **保留 Swing 作为 Spring Boot 界面** — 违背 Web 化目标，部署仍依赖桌面  
3. **Phase 1 同时重写 ATL + 前端 + 序列图** — 范围过大，易失败  
4. **继续硬编码 API Key** — 安全风险，必须在 Phase 1 改掉

## 13. 总结

将 RapidOOD 转为 Spring Boot **在技术和业务上均可行**：核心价值（模型转换、质量度量、LLM 增强）与平台无关，Bound 的主要是 Eclipse UI 与 RM2PT 插件耦合。

推荐策略：

> **「后端无头化优先、前端 Web 化其次、论文缺失能力第三期补齐」**

这样可以在 6 周内得到可演示、可集成 CI、可对外提供 API 的系统，并为后续回应期刊审稿中的「外部评估、方法对比」要求打下基础。
